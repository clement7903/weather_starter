-- Prompt Engineering -- 
Learn to use role, goal, context: 
1. Role is persistent different requests 
2. Role helps to anchor the model's behaviour (replies, how it acts, what it prioritizes etc )
3. Goal: Make sure if passes unit_test_1, unit_test_2 etc 
4. Context of which files to change, which files to take reference from etc


Learn to break up huge tasks into iterative prompting: 
What is the most stable layer or boundary I can define first?
How can I break this task so each step gives the next one better context?
What is the smallest version of this idea that would let me evaluate the direction quickly?
How can I prototype in a way that keeps experiments separate from production-quality code?
Use those questions to decide how to iterate. If the task is too broad, break it into layers or checkpoints. If the shape of the solution is still unclear, prototype the smallest useful version first. The goal is to create review points where you can steer the agent before complexity compounds.

Planning vs Direct prompting:
Before you switch into planning mode, ask yourself:
Would getting this task wrong be expensive to unwind?
Do I need the agent to clarify requirements before it starts implementing?
Would a visible task list help me review or steer the work more effectively?
If the answer to those questions is yes, plan first. A short planning pass gives you a chance to correct the direction before the agent starts building, which is usually much cheaper than correcting it after the implementation is already in flight.


-- Context Engineering -- 
The context window is the total amount of text a model can attend to in a single request. Your instructions, the conversation history, the files the agent has read, and any pasted documentation all compete for space inside that window.

Review the token usage. For copilot, it is at the bottom right window


Context Limit: 
1. Token-to-word Ratio depends on the AI model used. Can refer to convertors to estimate the number of tokens used: https://platform.openai.com/tokenizer
2. Multimodal (including text, video, audio data) models would also use tokens for other non-textual forms of data.
3. Context limit introduces context rot. The following are reasons why context rot occurs:

    Finite Attention Budget
    Models do not allocate attention evenly across an ever-growing prompt. As the amount of context increases, earlier instructions have to compete with more tokens for the model’s attention.

    Recency Dominance
    Recent tokens also tend to exert more influence than older ones. That makes fresh instructions, fresh code, and fresh errors feel more salient than constraints that were established much earlier in the thread.

    Error Accumulation
    Small mistakes can compound over time. Once an incorrect assumption enters the conversation, later turns may build on it as though it were true.

How to resolve?
When an agent starts drifting, do not just keep arguing with the same thread. Open a new one, restate the task, and bring forward only the decisions, files, and constraints that still matter. That reset is often faster than trying to repair a long conversation that has already started to rot.


How to remember the context?
- Use a persistent project level guidance which is injected into every reqeust sent to the agent (e.g. AGENTS.md, CLAUDE.md file)
- The file could be at the project level or individual nested directories where different services may need different language, framework or workflow instructions
- Create progressive disclosure by linking to other .md files for specific info (e.g. data schema is one file, repo structure is another file, techstack is another, framework is another one...) instead of adding everything into 1 .md file.

Sample instructions to put in .md file:
- progressive disclosure document locations
- test / code quality instructions
- git workflow
- staleness update instructions
- critical guardrails

How to create the AGENTS.md file?
- Using /init command for github copilot or direct prompting to the agent.

What are some ways to resolve token limits?
1. Compaction: summarizing info, deleting outdated/unnecessary info. Normally done by the agent automatically when a particular token limit is hit.
2. Structured Notes: Structured notes are plain text files, usually written in Markdown, that an agent can read in one session and reuse in a later one. AGENTS.md is one common example, but plans, handoff notes, and task summaries can all serve the same role. 
    
    It includes "Skills": reusable instructions that teach the agent how to perform a specific workflow or task. In practice, they are usually written as small Markdown files with a name, a short description, and step-by-step guidance the agent can follow. They will be covered in more detail in a later module.

How do the agents search for context in files?
- Search only visible files, normally will exclude .env and node_modules files.
- Embedding search: Code is split into smaller chunks before embedding it. 
    - As chunks splits logical sequential code, they can hide useful context.
    - Staleness is present in active codebases until the embedding store is rebuilt.
    - Efficient similarity search requires a separate vector database, not something that is local/lightweight.

Module 4: Agent Development

** Model Context Protocol (MCP) **
Model Context Protocol (MCP) gives agents a standard way to connect to external tools and data sources. Instead of every integration being custom-built for every tool, MCP makes those connections reusable. That matters because agentic systems are most useful when they can act on the world around them, not just reason over the text already in the prompt.

MCP is most useful when you have no better option. Because MCPs usually load tool definitions up front, they are less token efficient than skills. If the workflow can be packaged as a skill, prefer that. MCP is the fallback when it cannot.

** Skills **
Tools and MCP integrations usually expose their definitions up front when they are loaded. Skills are different: the agent first discovers that a skill exists, then loads the full instructions only when it decides the skill is relevant. That two-step pattern makes skills much more token efficient.

Skills explain the steps / "how" to do things while MCP provides the connectivity between external systems (e.g. databases) and the agent.

- Usually stored in SKILL.md file
- The following frontmatter is required at the top of SKILL.md:
    name: A short identifier
    description: When to use the skill
- The structure afterwards is flexible and should be designed around the workflow the skill is teaching. Some coding tools add their own conventions or formatting details for skills, so it is still worth checking the documentation for the specific tool you are using.
- Skills can do much more than wrap tool calls. They are also useful for packaging repeatable workflows, guardrails, and project-specific habits so the agent can reuse them consistently.

Where to find the SKILLs or MCPs?
- Use public registries such as
    https://registry.modelcontextprotocol.io/
    https://www.skills.sh/


** Subagents **
- Prevents context rot by assigning a mini agent for a specialized task.
- Each subagent to have the following:
    1. Model being used
    2. Clear role
    3. Tool permissions needed to do its task
- Some good areas for the use of subagents include:
    Code Review
    Security Review
    Front End
    Back End


Module 5 : Responsible AI

Methods:
1. Slop squatting: Slop squatting combines AI hallucinations with typo squatting. In traditional typo squatting, a hacker registers a domain like "gogle.com", hoping you mistype the URL. In slop squatting, the LLM makes the mistake for you.
2. Prompt Injection: manipulates the input provided to the AI to make it behave in unintended ways.
3. Confused Deputy: A confused deputy attack is when an attacker exploits a service which is otherwise authorised to perform certain activities with escalated privileges to instead perform unintended actions on behalf of the attacker.
